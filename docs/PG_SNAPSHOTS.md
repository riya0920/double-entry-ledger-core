# SE-1 — snapshot-backed balances on Postgres

Generated by `pg_snapshot_test.py` against `PostgreSQL 18.6 (Ubuntu 18.6-0ubuntu0.26.04.1) on x86_64-pc-linux-gnu`.

`README.md` listed this as the remaining Postgres work: *the derived
design fixes most of the contention and moves the cost to the read
path, where it grows with history ... periodic snapshots are [the
answer], and the SQLite side already has that machinery. Porting it is
the remaining work.*

## The finding: it is not a port

The SQLite version checkpoints *everything up to here*, which is a
moment that exists because SQLite serializes writers with a
database-level lock. Postgres runs writers concurrently, so it is not,
and the obvious translation is **silently and permanently wrong**.

`d_journal_entry.id` comes from an IDENTITY sequence, and **a sequence
value is allocated before the transaction commits.** So a transaction
holding a low id can still be in flight while one holding a higher id
has already committed. A snapshot that trusts `MAX(id)`:

- stores a watermark **above** an entry it could not see, so the
  checkpoint sum excludes it, and
- the delta query (`id > watermark`) then skips that same entry for
  being **below** the watermark.

The entry lands in neither half. Measured, with the interleaving
forced by two connections so it is a demonstration rather than a race:

| | entry id | watermark | id <= wm | snapshot says | full scan says | error |
|---|---|---|---|---|---|---|
| `drain=False` | 401 | 403 | yes | 20,605 | 28,382 | **-7,777** |
| `drain=True` | 404 | 406 | yes | 36,170 | 36,170 | **+0** |

**Nothing errors.** The arithmetic is self-consistent, the query
plan is fine, and the only way to see the -7,777 is to compare
against a full scan — which is the one thing a cache exists to
avoid doing. Every later snapshot inherits it, because each one is
built on the journal the previous one already mis-summed.

## The fix: drain, then sum

```
1. wm    <- MAX(id) visible now. The sequence is monotonic, so any
            transaction starting after this reads a value ABOVE wm.
2. xmax0 <- pg_snapshot_xmax(pg_current_snapshot()), the first xid not
            yet assigned. Every transaction that could still write an
            id <= wm has an xid below this.
3. wait until pg_snapshot_xmin(pg_current_snapshot()) >= xmax0 --
            i.e. every transaction in flight at step 2 has ended.
4. NOW sum entries with id <= wm. Each has committed or aborted, so
            the sum can never change again.
```

Step 3 is the entire difference. `take_snapshot(drain=False)` is kept
so the failure can be reproduced, and it is never the default; a drain
that times out **raises** rather than falling back to the undrained
watermark, because a snapshot that quietly degrades under load is worse
than no snapshot — load is exactly when it would be taken.

Drain wait in the clean run: **0.538s**.

## Read cost is measured elsewhere

`pg_snapshot_read.py` and `docs/PG_SNAPSHOT_READS.md` carry it, on one
long-lived connection. This file used to time `balance()` in a loop,
which opens a fresh connection per read and therefore measured a TCP
handshake plus SCRAM authentication -- reporting the full scan getting
*faster* as history grew. That section was removed rather than kept
with a caveat attached.

## What this does not claim

- **One forced interleaving.** It is a demonstration of a mechanism,
  not a measurement of how often it fires in production -- which
  depends on transaction duration and posting rate, and is not
  estimated here.
- **The drain has a cost that is not characterised.** It waits for
  every transaction in flight to end, so a long-running writer delays
  every checkpoint behind it. `DrainTimeout` bounds that wait and turns
  it into an error; what it does NOT do is say how often a busy system
  would hit the bound.
- **Still not the spec's 100K / 50-worker figure**, which remains
  unclaimed.
