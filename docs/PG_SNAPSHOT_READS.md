# SE-1 — read cost with and without a snapshot

Generated by `pg_snapshot_read.py` against `PostgreSQL 18.6 (Ubuntu 18.6-0ubuntu0.26.04.1) on x86_64-pc-linux-gnu`.

## The measurement mistake this file exists to correct

The first version of this benchmark timed `DerivedLedger.balance()` in
a loop. That method opens a **fresh connection per call**, so the loop
timed a TCP handshake plus SCRAM authentication once per read, and the
result was nonsense in a direction that should have been impossible —
the full scan got *faster* as history grew, 87.98ms at 1,000 entries
down to 29.19ms at 4,000.

`pg_store.py`'s own docstring already records this mistake on the write
path: *a connection per transaction ... made the drill 30x slower than
the database, so the benchmark was measuring connection setup and
reporting it as ledger throughput.* I reproduced it on the read path.

Everything below runs the two query shapes on **one long-lived
connection**, and leads with `EXPLAIN (ANALYZE, BUFFERS)` rather than
the clock: rows read and buffers touched are properties of the plan,
not of how busy this machine was.

## The second finding, and the diagnosis I got wrong

Draining makes the snapshot **right**. It does not make it **fast**,
and as ported it was not — the delta query read every entry for the
account and threw them all away:

```
Bitmap Heap Scan on d_journal_entry e  (actual rows=0)
  Filter: (id > s.watermark_id)
  Rows Removed by Filter: 200000
  Buffers: shared read=2029
```

The same buffer count the full scan touches. The checkpoint was
arithmetically correct and did no less work — the failure mode where a
cache looks fine **because the answer is right**, so no correctness
test can see it.

**I diagnosed it wrong.** It reads like a missing index, and I added
`(account_id, id)` on that basis. Isolating the two causes on 200,000
entries with replay depth zero says otherwise:

| | buffers | rows discarded | index chosen |
|---|---|---|---|
| no composite index, **no ANALYZE** | 8,283 | 200,000 | `ix_d_entry_account` |
| no composite index, ANALYZEd | 46 | 0 | `d_journal_entry_pkey` |
| composite index, ANALYZEd | 31 | 0 | `d_journal_entry_pkey` |

The index was never the problem. **A freshly bulk-loaded table has no
statistics**, so the planner estimated 514 rows for the account, chose
a bitmap scan over `(account_id)`, and discarded all 200,000. After
ANALYZE it used the PRIMARY KEY on `id` — which had been there the
whole time — and the delta became a range scan.

The third row is the one that settles it: with the composite index
present the planner **still** picks `d_journal_entry_pkey`. It never
uses the index I added. So the index is gone again, and an unused index
is not neutral — it is maintained on every insert, a write cost paid
for a read benefit that does not exist.

Operationally: a checkpoint taken right after a bulk load can be
correct and useless at once, and the fix is ANALYZE, not schema.

## Result

Every step ANALYZEs after its bulk load, for the reason above. The
isolation of that effect lives in `pg_snapshot_stats.py`, because
clearing statistics needs superuser and the ledger role is not one.

| entries | replay depth | full scan | snapshotted |
|---|---|---|---|
| 40,000 | 0 | 847 buf / 6.07ms | **12 buf** / 0.27ms |
| 80,000 | 0 | 1,496 buf / 12.30ms | **12 buf** / 0.57ms |
| 120,000 | 0 | 2,244 buf / 18.26ms | **12 buf** / 0.35ms |
| 160,000 | 0 | 5,984 buf / 20.72ms | **16 buf** / 0.27ms |
| 200,000 | 0 | 7,480 buf / 22.83ms | **16 buf** / 0.44ms |

| | at 40,000 entries | at 200,000 entries | growth |
|---|---|---|---|
| full scan | 847 buf | 7,480 buf | 8.8x |
| snapshotted, ANALYZEd | 12 buf | 16 buf | 1.3x |

**The full scan's work grows with history; the snapshotted read's
does not** — 16 buffers against 7,480 at 200,000 entries, a
**468x** reduction, in a number the host's load cannot move.

The mechanism is the `replay depth` column. A checkpoint holds the
number of entries a read must touch to roughly a constant regardless of
how long the account has existed — which is why neither extreme, cached
balance or pure derivation, was the answer.

**The write path is untouched.** `post()` passes straight through to
`DerivedLedger`; a checkpoint that changed the write path would hand
back the contention the derived design was built to remove. And after
the index was removed there is no new write cost to account for.

## What this does not claim

- **The timings are the weak column.** This machine runs several other
  projects' services; the milliseconds are a floor with real noise in
  them. The rows-read and buffers columns are the evidence.
- **History is bulk-inserted**, not posted through the ledger. The
  write path is `pg_hotrow_test.py`'s subject; paying its per-posting
  cost would turn a 200,000-entry read benchmark into an hour of
  writes. So this measures read shapes over a realistic *volume*, not
  a realistic write history.
- **One hot account**, and every snapshot is taken immediately before
  the read that benefits from it — the best case. A real cadence leaves
  a replay tail, and that tail is the number that would matter in
  production.
- **Snapshot-sweep cost is not measured.** `take_snapshot` sums every
  account at a watermark; on one account that is cheap and at scale it
  is a periodic full pass. The read side of the trade is measured here
  and the checkpoint side is not.
- **Still not the spec's 100K / 50-worker figure**, which remains
  unclaimed.
