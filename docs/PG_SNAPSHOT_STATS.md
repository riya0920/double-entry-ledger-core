# SE-1 — a missing index, or missing statistics?

Generated by `pg_snapshot_stats.py` against `PostgreSQL 18.6 (Ubuntu 18.6-0ubuntu0.26.04.1) on x86_64-pc-linux-gnu`.

## The symptom

The snapshotted balance read was **correct and saved nothing**. With
the replay depth at zero it still read every entry for the account and
discarded all of them:

```
Bitmap Heap Scan on d_journal_entry e  (actual rows=0)
  Filter: (id > s.watermark_id)
  Rows Removed by Filter: 200000
  Buffers: shared read=2029
```

That is the same buffer count the full scan touches — the failure mode
where a cache looks fine **because the answer is right**, so no
correctness test can see it.

## The diagnosis I made, and the one the experiment supports

I read it as a missing index — the derived schema indexes
`(account_id)` alone, so nothing lets the delta start at the watermark
— and added `(account_id, id)`. This is the experiment that should have
come first: 200,000 entries, replay depth zero, two candidate causes
separated.

| | buffers | rows discarded | index chosen |
|---|---|---|---|
| no composite index, NO ANALYZE | 8,283 | 200,000 | `ix_d_entry_account` |
| no composite index, ANALYZEd | 46 | 0 | `d_journal_entry_pkey` |
| composite index, ANALYZEd | 31 | 0 | `d_journal_entry_pkey` |

**Statistics, not indexes.** A freshly bulk-loaded table has none,
so the planner mis-estimated the account's row count, chose a
bitmap scan over `(account_id)`, and discarded every row. After
ANALYZE it used the **primary key on `id`** — which had been there
the whole time — and the delta became a range scan.

Row C settles it: with the composite index present the planner
**still** picks `d_journal_entry_pkey`. It never uses the index I added.

So the index was removed again. An unused index is not neutral —
it is maintained on every insert, a write cost paid for a read
benefit that does not exist.

## What it means operationally

A checkpoint taken right after a bulk load can be **correct and
useless at the same time**, and the fix is ANALYZE, not schema. Worth
stating plainly because *it must need an index* is the reflex, and it
was mine.

## What this does not claim

- **One table, one account, one shape of query.** This says nothing
  about whether other queries in this repo want other indexes.
- **Autovacuum would eventually have analyzed the table.** The window
  measured here is the one between a bulk load and that happening,
  which is exactly when a first checkpoint gets taken.
- **Buffer counts, not timings.** Deliberately: this machine is busy
  enough that the clock would be the weaker evidence.
